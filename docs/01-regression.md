# 回归报告：微信 4.1.11+ 内存密钥扫描失效

> 复现环境：Windows 11 / Weixin.exe **4.1.13.65** / Python 3.13
> 被测工具：`wechat-decrypt`（内存扫描版，`find_all_keys_windows.py`）

## 症状

解密流程本身不报错，但**静默丢数据**：

1. 微信新建了消息分片 `message_1.db`
2. 解密输出出现 `SKIP: message\message_1.db (无密钥)`
3. `message_0.db` 正常解密，于是导出结果看起来"只是少了一点"
4. 实际上**最近数月的全部消息都缺失**，而且没有任何警告

这是最危险的一种失败形态——不是崩溃，是安静地给出不完整的结果。

## 环境事实

| 项 | 值 |
|---|---|
| Weixin.exe 版本 | 4.1.13.65 |
| 版本目录 mtime | 2026-09-10（微信本次安装/更新的时间） |
| `Weixin.dll` 大小 | 188.9 MB |
| PE | PE32+ / x64, ImageBase `0x180000000` |
| `all_keys.json` | 缓存自 2026-06-02，共 18 条，**不含新分片** |

## 根因

### 1. 密钥缓存永不刷新

`main.py` 的取密钥逻辑：

```python
keys = strip_key_metadata(keys)
if keys:
    print(f"[+] 已有 {len(keys)} 个数据库密钥")
    return          # ← 只要 key 文件存在就直接返回，永不重扫
```

`all_keys.json` 是**一次性快照**。微信之后新建的任何数据库都拿不到密钥，
且被静默跳过。

### 2. 密钥不再以字符串形式驻留内存

旧版在内存中缓存 `x'<64hex_enc_key><32hex_salt>'`。
`find_all_keys_windows.py` 用正则 `x'([0-9a-fA-F]{64,192})'` 扫描该模式。

**4.1.13.65 上该模式已完全不存在。**

## 证据

以下测试均在本机、对本人账号的 Weixin.exe 进程执行。

### 测试 A：内存可读性（排除权限问题）

以管理员身份枚举 7 个 `Weixin.exe` 进程，成功读取 **1.9 GB** 内存。
内存读取本身完全正常——不是权限问题。

### 测试 B：扫描器返回 0 命中

```
扫描完成: 3.5s, 7 个进程, 0 hex模式
结果: 0/22 salts 找到密钥
```

`x'` 字节序列在内存中出现 9047 次，但**没有一次后面跟着合法的 hex 密钥串**。

### 测试 C：已知有效密钥是否在内存中

取一把**已验证可用**的 `enc_key`（能通过 SQLCipher page-1 HMAC 校验），
生成 44 个变体全量搜索内存：

| 变体 | 命中 |
|---|---|
| raw 32 字节 | 0 |
| hex 小写 / 大写 | 0 |
| base64 | 0 |
| XOR 0x80 | 0 |
| 字节反转 | 0 |
| 全部 18 把 key 的 raw 形式 | 0 |
| 全部 18 把 key 的 hex 形式 | 0 |
| **salt 的 ASCII hex** | **0** |

结论：**密钥与旧格式字符串都已不在进程内存中。**

### 测试 D：salt 附近是否存在密钥描述符

salt 的**原始 16 字节**在内存中出现 2 次。以每处为中心 ±16 KB 穷举
每一个 32 字节窗口，逐个用 page-1 HMAC 校验：

```
未找到。共校验 339051 个候选窗口。
```

### 测试 E：能否从旧密钥推导新密钥

18 组 (key, salt) 两两测试代数关系：

- `key_i XOR salt_i` 是否恒定 → **不恒定**（18 种结果）
- `key_i XOR key_j == salt_i XOR salt_j` → **0/153 成立**
- key 字节熵 → 228/256 种取值（576 字节样本）

结论：key 是 KDF 的随机输出，**无法从旧密钥推导新密钥**。

### 测试 F：是否发生了「密钥轮换」（关键）

把 6 月快照中记录的每个库的 `salt`，与该文件**当前**文件头前 16 字节逐一比对：

```
salt 未变: 17 / 18
salt 已变:  1 / 18   （message_resource.db，该库被重建过）
```

**17 个数据库的 salt 一字未变，且它们的 6 月密钥至今仍能通过 HMAC 校验。**

这条证据推翻了「微信轮换了密钥」的假设。真实情况是：

| | 是否变化 |
|---|---|
| `password`（账号主密钥） | **不变**（否则旧密钥不可能仍然有效） |
| 各库 `salt` | 不变（已存在的库） |
| 各库 `enc_key` | 不变（派生自上述两者） |
| **新库**（`message_1.db` 等） | **有新 salt → 新 enc_key**（正常建库行为，非轮换） |
| 内存中的**存放形式** | **变了** ← 唯一真正的变化 |

所以失效的**不是密钥，是提取方法**。这一点很重要：它意味着

> **只要能拿到那个长期稳定的 `password`，加上任意文件的 `salt`，
> 就能派生出该文件（含所有新分片）的 `enc_key`。**

不存在「每次更新都要重新对抗」的军备竞赛，缺的只是一个静态常量。

## 实际的新机制

社区参考实现（见文末）已经确认了 4.1.11+ 的变更：

```
password ≠ enc_key

enc_key = PBKDF2-HMAC-SHA512(password, salt, 256000, 32)
salt    = 数据库文件头前 16 字节
```

- 内存中保存的是 **password**（32 字节，KDF 的*输入*），不是可直接使用的 `enc_key`
- 因此"在内存里找 enc_key"这个方向**从根上就是错的**——测试 C/E 的零命中是必然结果
- password 位于 codec 配置函数的参数结构中，需要 **Frida spawn 早期注入**才能捕获
- 参考实现同时指出该路径**存在 anti-hook 检测**

加密参数（SQLCipher 4，未变）：

```
AES-256-CBC + HMAC-SHA512
page_size = 4096, reserve = 80
布局: [0:16]=salt | [16:4016]=数据 | [4016:4032]=IV | [4032:4096]=HMAC
```

## 结论

| 问题 | 状态 |
|---|---|
| 旧内存扫描方案 | **已失效**，不可修复 |
| `all_keys.json` 静默跳过新分片 | **设计缺陷**，应至少告警而非静默跳过 |
| 完整密钥提取 | 需 Frida + 运行时验证，本仓库未提供 |
| **近期消息缺失** | **已由 FTS 兜底方案解决**，见 [02-fts-fallback.md](02-fts-fallback.md) |

## 建议 upstream 的两处改动

1. **密钥缓存应失效重扫**：`all_keys.json` 中缺少当前存在的任一 db 时，
   应触发重新扫描，而不是直接 return
2. **跳过必须告警**：`SKIP: <db> (无密钥)` 应当在最终输出中汇总为
   显式警告（例如 `⚠️ 3 个数据库未解密，导出结果不完整`），
   而不是混在逐行日志里
