# 非注入路径尝试：Windows 调试 API + 硬件断点

> 环境：Windows 11 / Weixin.exe 4.1.13.65 / Python 3.13
> 目标：不向微信进程注入任何模块、不修改其代码，捕获 codec 配置函数入参

## 动机

社区方案（见 [01](01-regression.md)）用 Frida 注入 agent DLL 并 inline hook 目标代码。
这条路能成，但代价明确：

| | Frida | 本方案 |
|---|---|---|
| 向目标加载模块 | 是（frida-agent） | **否** |
| 修改目标代码 | 是（inline hook 打补丁） | **否**（硬件断点，目标内存零改动） |
| 附加方式 | 注入 | `DebugActiveProcess` / `CreateProcess(DEBUG)` |

思路：用 Windows 原生调试 API + **CPU 的 DR0–DR3 硬件断点**，拿到与 hook 相同的信息。

## 结论先行

**机制本身已验证可用**，但**登录瞬间的捕获未能打通**，卡在三个具体障碍上。
本文把已验证的部分和三个坑都记录下来，避免后来人重复。

## 一、已验证可用的部分

### 1.1 机制自检（无害靶子）

用 `notepad.exe` 当靶子，在它自己的入口点下硬件执行断点：

```
[*] 靶子: notepad.exe  AddressOfEntryPoint=0x19C0
[+] 已以调试方式启动 PID=19772
    CREATE_PROCESS hProcess=436 lpBaseOfImage=0x7FF712FB0000
    设置硬件断点 @0x7FF712FB19C0 -> 成功
    LOAD_DLL ... ×16
    初始断点 @0x7FFF12A02239
  ★ 硬件断点命中! addr=0x7FF712FB19C0 rcx=0xFCDF15A000 rip=0x7FF712FB19C0
[*] 事件 46 个, 硬件断点命中 1 次
✅ 全套机制可用
```

**只命中一次就正常继续**，说明 RF（Resume Flag）处理正确，无死循环。

### 1.2 真实微信上附加成功

对**正在运行**的微信进程附加（不重启、不改代码）：

```
[*] 已附加到 PID=<pid>（不注入、不改代码）
    [+] Weixin.dll @ 0x7FFE3C6F0000
    [+] 断点地址 = 0x7FFE3FD24F10
    字节校验: 目标=4883ec48488b05e5 磁盘=4883ec48488b05e5 ✅ 一致
    [+] 已在 118 个线程设置断点
  [  10.2s] hit #1 rcx=0x2465F9A6920
  ...
  [  10.3s] hit #20 rcx=0x246601BBBD0
```

**关键点：字节校验通过** —— 目标进程内存中该地址的字节与磁盘上 `Weixin.dll`
对应 RVA 的字节完全一致，证明**模块基址识别正确、断点位置正确**。

### 1.3 空闲状态下的行为

- 该函数在**空闲时也会被调用**，但频率不高：**21 次 / 90 秒**
- 这与社区报告的「单次登录触发上万次」一致 —— 说明高频调用集中在**登录/建库阶段**
- 捕获到的 21 个 `rcx` 中**不含 password**（经 PBKDF2 + 已知 `(salt, enc_key)` 校验）

## 二、三个未打通的障碍

### 障碍 1：调试模式**启动**被反调试拦截

用 `CreateProcess(..., DEBUG_PROCESS, ...)` 启动 `Weixin.exe`：

```
[*] 已以调试方式启动 PID=18472（DEBUG_PROCESS：整个进程树）
    [+] PID 18472: Weixin.dll 后加载 @ 0x7FFE3C6F0000 BP=0x7FFE3FD24F10
    [+] PID 18472: 已在 4 个线程设置断点
```

模块加载、断点设置**全部成功**，但——

```
Get-Process -Id 18472 | Select MainWindowTitle
→ 空
WS = 100MB（不增长）
```

**进程存活、DLL 已加载，但始终不创建窗口。** 即微信检测到调试器后拒绝继续启动 UI。

**这是"调试启动"与"附加"的重要差异**：
- 启动时被调试 → 微信可检测并中止
- 已运行后附加 → 实测**未被拦截**（1.2 节的 21 次命中即证据）

### 障碍 2：登出/登录会**替换主进程**

实测某次登出→登录前后：

```
登出前: 主进程 PID=26728 (359MB)  ← 附加对象
登出后: PID 26728 已退出
        主进程变为 PID=7380 (320MB)
```

**单 PID 附加会随登出一起失效**，断点消失。

值得注意的是：`7380` 在登出前**已经在运行**（当时 191MB）。它只是登录后变成主进程。
这意味着「登录前把所有 Weixin.exe 都附加一遍」理论上可以覆盖。

### 障碍 3：全进程附加遭遇**事件风暴**

按障碍 2 的思路实现"全进程附加 + 持续监视新进程"后：

```
[+] 附加 PID=3168 (36MB)   已附加 1 个
[+] PID 3168: Weixin.dll @ ... BP=... ✅  已在 11 个线程设置断点
[+] 附加 PID=4760 (8MB)    已附加 2 个
[+] 附加 PID=24692 (8MB)   ...
[+] 附加 PID=28932 (103MB) ... 已在 66 个线程设置断点
[+] 附加 PID=18420 (32MB)  ...
[+] 附加 PID=9928 (32MB)   ...
    ... 300s, 事件 10183730, 附加 6, 命中 0
```

**6 个进程全部附加成功、断点全部设置成功（字节校验 ✅），但 300 秒内产生
10,183,730 个调试事件（约 34,000/秒），命中 0。**

事件速率远超正常的线程创建/退出。最可能的原因是**微信在自身代码中进行单步自陷
（anti-debug 手法之一）**，产生海量 `EXCEPTION_SINGLE_STEP`，淹没了调试循环。

> 注意：障碍 1.2 的单进程附加也是同一套代码，只是当时未统计事件数 ——
> 风暴可能当时就存在，只是 21 次命中仍挤了出来。

## 三、三个可复用的技术点

无论后续走哪条路，以下三点已验证有效：

### 3.1 用 `SizeOfImage` 识别模块（规避 ASLR）

附加模式下拿不到 `LOAD_DLL` 事件来获知模块名。做法：

1. 从磁盘读 `Weixin.dll` 的 `SizeOfImage`
2. `EnumProcessModulesEx` 枚举目标进程全部模块
3. 逐个读 PE 头取 `SizeOfImage`，与磁盘值比对

`Weixin.dll` 4.1.13.65 的 `SizeOfImage = 0xBD5B000`（约 189 MB），
在 138 个模块中**唯一命中**。

### 3.2 硬件执行断点的正确设置

```python
ctx.Dr0 = addr
ctx.Dr7 = (ctx.Dr7 & ~0xF0000) | 0x1
#         ↑ 清 LEN0/RW0 位      ↑ L0=1 使能, R/W0=00(执行), LEN0=00(1字节)
```

### 3.3 **必须设置 RF，否则死循环**

硬件执行断点触发后，**必须在 EFlags 中置 RF（Resume Flag）**，
否则放行后会在同一条指令上立刻再次触发：

```python
ctx.EFlags |= 0x10000   # RF
SetThreadContext(thread, ctx)
```

实测：不置 RF 会死循环；置 RF 后「命中一次 → 正常继续」。

## 四、给继续研究的人

**如果要在非注入路径上继续，方向是解决障碍 3 的事件风暴：**

1. **只在特定时间窗启用断点** —— 平时不加 DR0，仅在检测到登录动作时才挂
2. **过滤单步异常** —— 不在 `bp_addr` 上的 `EXCEPTION_SINGLE_STEP` 直接放行，
   并考虑降低其产生速率（需要先搞清微信为何产生海量单步）
3. **换用 `DebugActiveProcessStop` 更细粒度地管理附加集合**

**如果接受注入，则社区方案（Frida + spawn）已验证可行**，见 [01](01-regression.md) 参考节。

**风险提示**：无论哪种，反调试/反 hook 检测的存在意味着账号风险无法完全排除。
本项目作者未在真实账号上完成过登录瞬间的捕获。

## 五、代码

`tools/hwbp_debugger.py`

| 模式 | 说明 |
|---|---|
| `--attach-all` | 附加所有 Weixin.exe 并持续监视新进程（非注入，本文主要实验对象） |
